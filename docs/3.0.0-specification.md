# Omnibar 3.0.0

One observation surface. No delegate, no action slot, no companion library.

Status: specification. Nothing here is implemented. Assumes 2.2.0 has shipped.

## Why a major version

2.2.0 added an observation bus and left both legacy slots in place, so an
Omnibar now has three ways to tell you the same thing. That was the right
shape for an additive release and is the wrong shape to keep: every reader of
`Omnibar.swift` has to learn all three and their interaction order, and every
doc comment has to qualify itself.

3.0.0 removes the two that predate the bus.

The breakage budget is set by there being no third-party consumers. Every call
site is in apps under the author's control, so a deprecation ladder would be
scaffolding built for nobody. RxOmnibar targets the pre-2.0.0 API, has already
sat out one major version, and gets *easier* to port against this surface —
`Observable.create` wrapping `observe(_:)` needs no `DelegateProxy` and no
`@objc` protocol, which is the thing that blocked it.

## Removed

| Symbol | Replacement |
|---|---|
| `Omnibar.omnibarContentChangeDelegate` | `observe(_:)` or `events()` |
| `OmnibarContentChangeDelegate` | `OmnibarEvent` |
| `Omnibar.moveFromOmnibar` | `.movement` case of `OmnibarEvent` |
| `MoveFromOmnibar` | closure passed to `observe(_:)` |
| `AsyncOmnibar` product and target | `Omnibar.events()` |
| `OmnibarEvents` | `Omnibar.events()` |

`MovementEvent` survives unchanged — it is a good value type and the payload of
`OmnibarEvent.movement`. `OmnibarContent`, `OmnibarContentChange`,
`ChangeMethod`, `display(content:)`, `commit()`, `focus()`,
`focusAndClearText()`, `textInsets`, `isResettable`, and
`alwaysFireWhenClearingText` are untouched.

Deleting `MoveFromOmnibar` also deletes the reason `finish()` could never tell
whether it still owned the movement slot: a struct wrapping a closure has no
identity to compare. That question stops existing rather than getting a better
answer.

## The surface

```swift
extension Omnibar {

    /// Stops delivery when cancelled or released.
    @MainActor
    public final class Observation {
        public func cancel()
    }

    /// Registers `handler` for every event, in registration order.
    ///
    /// Delivery stops when the returned observation is cancelled or released,
    /// so the caller must hold it. Capture the Omnibar weakly in `handler`.
    public func observe(
        _ handler: @escaping @MainActor (OmnibarEvent) -> Void
    ) -> Observation

    /// Returns a stream of every event from this point on.
    ///
    /// Ends when the consuming task is cancelled or the Omnibar deallocates.
    public func events(
        bufferingPolicy: AsyncStream<OmnibarEvent>.Continuation.BufferingPolicy = .unbounded
    ) -> AsyncStream<OmnibarEvent>
}
```

Both survive because they are not redundant. `observe(_:)` delivers in the same
turn as the event; `events()` delivers on a later one. Arrow-key movement wants
the first — routing it through a stream lands the selection change a turn
behind the text change that accompanied it. Search wants the second.

### `observe(_:)` is not `@discardableResult`

Dropping the observation stops delivery. This is the one place the two halves
of the API could have diverged and should not.

The reason `events()` needs no token is that `yield` reports `.terminated` when
its consumer is gone — the transport announces its own death. **A closure has
no equivalent signal.** A handler that captured everything weakly and now does
nothing is indistinguishable from one doing real work, so `observe(_:)` needs
someone to say when to stop. That asymmetry is intrinsic, not an oversight.

2.2.0 got this wrong in a specific way, verified rather than assumed: with
`@discardableResult` and no cancellation on release, five `observe` calls whose
tokens are immediately dropped leave five live registrations, and a handler
whose captured object is deallocated still runs on every event forever. The
Omnibar itself still deallocates — this is unbounded growth within its
lifetime, not a leak that outlives it.

The trilemma is that `@discardableResult`, cancel-on-release, and no silent
failure cannot all hold. Marked discardable *and* cancelling on release,
`omnibar.observe { }` would register and immediately unregister, and the
handler would silently never fire. `AnyCancellable` resolves this the same way
this specification does: the token is not discardable, and letting it go stops
the work.

### How cancellation on release is implemented

Not with `deinit`. Verified: a plain `deinit` cannot call `removeObserver`,
because that method is main-actor isolated and a `deinit` is not —

```
error: call to main actor-isolated instance method 'removeObserver'
       in a synchronous nonisolated context
```

Only `isolated deinit` compiles. The manifest now requires 6.2, so that is
available — but it is still the wrong mechanism here.

Instead **the Omnibar holds each observation weakly** and drops entries whose
token has died, at the next dispatch — exactly how sinks are already dropped
when `yield` returns `.terminated`. A prototype confirms the semantics: a
dropped token is pruned and never fires, a held token fires, and `cancel()`
stops delivery.

Two reasons this beats `isolated deinit` even where both compile. It gives both
halves of the API one pruning rule instead of two, which is the symmetry the
rest of this document keeps buying. And `isolated deinit` is not the more
deterministic option it looks like: when the last release happens off the main
actor the body is scheduled onto it rather than run in place, so cleanup is
deferred there too — the same lazy reclamation, reached by a more complicated
route.

## Dispatch

```
emit(event):
    drop dead observations and terminated sinks
    snapshot observers and sinks
    append event to the pending queue
    if already dispatching: return
    for each queued event:
        deliver to the snapshot, observers before sinks
```

**Ordering guarantees**, each to be pinned by a test:

1. Observers receive events in registration order.
2. A recipient registered during a dispatch — observation *or* stream — does
   not receive the in-flight event. It receives the next one.
3. A recipient cancelled during a dispatch still receives the in-flight event.
4. An event caused by a handler is delivered after the event that caused it,
   to every recipient.
5. Esc emits the `.contentChange` for the emptied text before `.cancel`. Pin
   this on *both* paths — the already-empty field and a field with text, where
   the change arrives through `fieldEditor.delete(self)` → `textDidChange`.
   2.2.0 covers only the first.

Guarantee 2 is a change. In 2.2.0 a stream created mid-dispatch receives the
in-flight event while an observation does not, because `observers` is copied by
the `for`-loop before handlers run while `sinks` is read fresh afterwards.
Nobody chose that; it fell out of the order of two statements and was then
written down as a promise. Snapshotting both at dispatch start removes the
split and two sentences of documentation with it.

### Re-entrancy, and why deferral is safe here

Delivery is queued, not nested: a handler calling `display(content:)` has the
resulting event delivered after the current one finishes, to every recipient.
Without the queue, one observer's echo would reach a second observer before the
event that caused it.

2.2.0 shipped a bug worth recording, because 3.0.0 must not reintroduce it.
Routing the *delegate* through this queue broke the standard AppKit idiom of
holding a flag across `display(content:)`: the flag was clear by the time the
echo arrived, so the delegate displayed again, queueing another echo — an
unbounded main-thread loop from delegate code that was correct in 2.1.0. A
guarded delegate reached a probe's abort cap of 50 re-entries where 2.1.0 stops
at one. The fix was to notify the slots where the event arises.

That hazard does not transfer to observers, because **an echo is
self-identifying**: `ChangeMethod.programmaticReplacement` marks exactly the
changes that `display(content:)` produced, and the Example already branches on
it. Callers migrating off the delegate should filter by `method`, not by a
flag. The migration note must say so.

An observer that responds to `.programmaticReplacement` by displaying again
still loops, and now spins the main thread instead of overflowing the stack
with a readable backtrace. Whether to bound the queue and trap is left open;
the cost of not doing it is a hang with no diagnostic.

## The Example app

Converting the Example to the bus in 2.2.0 left the delegate API with no
runnable demonstration. In 3.0.0 that stops mattering, because the delegate is
gone — the Example demonstrates the only surface there is. It should use
`observe(_:)` for movement and `events()` for search, so both halves are
exercised and the timing distinction is visible in real code rather than only
asserted in tests.

## Out of scope

- **Arrow keys are swallowed unconditionally.** `doOmnibarCommand` returns
  `true` for every movement selector whether or not anyone is listening, so an
  Omnibar with no observers eats the keystroke instead of passing it to the
  next responder. Pre-existing, orthogonal to observation, and gating it on
  "has a recipient" is unpredictable once streams exist — a registered but
  unconsumed sink is indistinguishable from a real listener.
- Eager sink pruning via `onTermination`. Prune-on-dispatch is now the uniform
  rule for both halves; adding a second mechanism for one of them would undo
  the symmetry this specification is buying.
- Anything in `OmnibarContent` / `OmnibarContentChange` / `ChangeMethod`.

## Migration

Mechanical, and the compiler finds every site.

```swift
// 2.x
omnibar.omnibarContentChangeDelegate = self
omnibar.moveFromOmnibar = MoveFromOmnibar { [weak table] in table?.move($0) }

func omnibar(_ o: Omnibar, didChangeContent c: OmnibarContentChange, method: ChangeMethod) { ... }
func omnibar(_ o: Omnibar, commit text: String) { ... }
func omnibarDidCancelOperation(_ o: Omnibar) { ... }

// 3.0.0
observation = omnibar.observe { [weak self] event in
    switch event {
    case let .contentChange(change, method): ...
    case let .commit(text): ...
    case .cancel: ...
    case let .movement(movement): ...
    }
}
```

Two things do not show up as compile errors and belong in the release notes:

- **Store the observation.** Dropping it stops delivery, silently.
- **Filter echoes by `method`, not by a flag.** A delegate that suppressed its
  own echo by bracketing `display(content:)` will not work as an observer,
  because the echo arrives after the bracket closes. Check
  `method != .programmaticReplacement` instead.

## Decisions rejected

- **Keeping one reserved delegate slot** beside the bus, as AppKit controls do.
  The argument is real: Cocoa's one-delegate rule exists because delegate
  methods return answers, and there is no combinator for two `Bool`s from two
  strangers. It does not apply here — every callback in this API returns
  `Void`, so nothing is being asked, only told.
- **Giving `MoveFromOmnibar` an identity token** so teardown could tell whose
  handler it was holding. Cheap, and moot: with no slot to displace, there is
  nothing to identify.
- **Making `events()` the only entry point.** It would delete `Observation` and
  its lifetime question outright, which is genuinely tempting. Rejected because
  synchronous delivery has a real use — arrow-key selection in the same turn as
  the keypress — and forcing it through a `Task` makes the selection trail the
  text.
- **A deprecation ladder through 2.3.** Warnings in every build for a migration
  with no external audience.
